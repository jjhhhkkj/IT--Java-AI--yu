生产级工程化——从“能跑通”到“能上线”
RAG 和工具调用让 AI 具备了业务能力，但一个能在生产环境中稳定运行、成本可控、可观测的 Java AI 系统，还需要解决四个工程化问题。

流式响应与前端交互
AI 对话的“打字机效果”不是锦上添花，而是用户体验的基本预期。技术实现上，后端通过 Spring AI 的 ChatClient 结合 WebFlux 的 Flux 推送数据块，前端用 SSE 或 WebSocket 接收并逐字渲染。关键设计是异步非阻塞：AI 生成一个 token 就推送一个 token，而不是等完整回复生成后再返回。这要求后端的线程模型从传统的阻塞式切换到响应式，前端需要处理流的中断、重连和错误恢复。

成本控制的三层防线
模型调用成本是 AI 业务项目最容易被低估的支出。三层防线的设计思路是：语义缓存将相似问题映射到已缓存的回答，余弦相似度超过阈值直接返回历史结果，避免重复调用模型。模型路由根据任务复杂度选择不同档位的模型，简单问答用轻量模型，复杂推理用推理模型，而非所有请求都走最贵的模型。上下文压缩裁剪无效的历史对话，只保留与当前问题相关的上下文。实测数据表明，Token 缓存优化可以将接口成本降低 40% 以上。

可观测性与评估体系
AI 系统的可观测性不是看日志里的报错，而是追踪从输入到输出的全链路：用户问了什么、检索到了哪些片段、模型用到了哪些工具、最终输出了什么、延迟和 Token 消耗是多少。Spring AI 的评估模块提供了评估用例和指标的编写能力，但工程化落地需要将这些指标接入现有的监控体系。一个常见的做法是在 AI 服务的调用链路中嵌入 Micrometer Tracing，将每次模型调用的延迟、Token 数和工具调用次数作为指标上报。

安全底线与降级策略
AI 系统必须假设模型会出错。安全底线包括：敏感数据在进入模型之前完成脱敏，模型输出在返回给用户之前经过内容过滤，工具调用在执行之前经过权限校验。降级策略是在模型服务不可用时的备用路径：缓存回答、规则引擎兜底、或明确告知用户“AI 服务暂时不可用，请稍后重试”。DDD 六边形架构中，LLM 调用被设计为可替换的端口，编译期隔离确保更换模型供应商不影响业务逻辑。

从技术选型和分层架构，到 RAG 与工具调用的工程实现，再到流式交互、成本控制、可观测性和安全降级，这套技术链路构成了 Java AI 业务项目从零到生产可用的完整路径。Java 在这个链路中的核心价值不是训练模型，而是让模型能力在企业系统中可靠运行。
